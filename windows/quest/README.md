# Quest: Open on Quest, control page, flags, history, SKYBOX

The PC companion drives **Quest Browser** over **adb over Wi-Fi** and the browser's DevTools socket (the one `chrome://inspect` uses). Everything goes through [`Watch-LoopSegmentsQuestLanTab.ps1`](Watch-LoopSegmentsQuestLanTab.ps1) (generic headset layer, incl. the DevTools helpers: [quest_tools](../../../../quest_tools/README.md), found by [`QuestToolsPath.ps1`](QuestToolsPath.ps1); companion hooks in [`QuestCompanionHooks.ps1`](QuestCompanionHooks.ps1), shared code of the double-click tools [`Set-LoopSegmentsQuestProximitySensor.ps1`](Set-LoopSegmentsQuestProximitySensor.ps1), [`Set-LoopSegmentsQuestWifiOff.ps1`](Set-LoopSegmentsQuestWifiOff.ps1) and [`Reset-QuestBrowserFlags.ps1`](Reset-QuestBrowserFlags.ps1) in [`QuestWrapperCommon.ps1`](QuestWrapperCommon.ps1)). Log: `%TEMP%\loopsegments-quest-lantab.log`.

| When | What | Setting |
|------|------|---------|
| **Open on Quest** click (PC LAN page) | Open the **Quest control page** in its own tab, then the LAN page in a **normal tab, signed in** (in front), then check the flag in that tab (below); on success **POST `/keep_alive.json`** (`action=extend`) to **add 60 min** Keep Alive on the phone (build **440+**) | `questSendLanLogin`, `questControlPageOnQuest` |
| Companion **startup**, until close | Keep the headset **awake**: proximity sensor held off once the headset is on adb | `questKeepAwakeDuringSession` |
| Companion **startup**, until close | While 3d_playlist_local's **XR page plays** on the Quest, **POST `/keep_alive.json`** (`action=reset`) every **10 min**, so the phone's Keep Alive (its LAN server, the rclone **L:** mount) does not run out mid-session ([Keep Alive while the Quest plays](#keep-alive-while-the-quest-plays)) | `questKeepAwakeDuringSession` (same job) |
| Companion **startup**, until close | Add this repo's tiles to the **Quest control page** on this PC's LAN address (quest_tools hosts it; 3d_playlist_local workflows add theirs): **SKYBOX Push / Update / Clear** buttons and **Measure LAN** (PC ↔ phone bandwidth) | `questControlPage`, `questSkyboxWebDav`; port: quest_tools `controlPort` (falls back to `questControlPort`) |
| Companion **close** (normal finish and the console-X watchdog) | Take this repo's tiles off the control page, close Quest Browser **tabs on the phone LAN page, the control page and every other page in quest_tools' shared origin list** (e.g. 3d_playlist_local's XR page), delete their **history entries** and sweep their *Recently closed* items, close Quest Browser itself if Open on Quest started it and no other tabs are left (other history is kept; if nobody is wearing the headset, a background helper does it once you put it on, within 2 h: [After-quit history helper](#after-quit-history-helper)), **remove the Loop Segments entries from SKYBOX** (phone WebDAV servers and the rclone DLNA entry), then turn the **proximity sensor back on**, open **Settings > Wi-Fi** and switch the headset's **Wi-Fi off** ([Wi-Fi off at close](#wi-fi-off-at-close)) | `questCloseLanTabsOnExit`, `questClearHistoryOnExit`, `questSkyboxWebDav`, `questKeepAwakeDuringSession`, `questWifiOffOnExit` |

Startup and close steps are skipped (and logged) when the headset is not on adb. **Open on Quest** waits instead (below).

**Headset asleep or off adb when you click:** the click is queued. The button says *Queued: opens on Quest when the headset wakes (until HH:MM)*, and the companion keeps polling for **7 minutes**; when the headset wakes and adb is back it opens the page once. It checks about every **5 s** (`-PollSeconds`, at least 2 s); while the headset is unreachable each check first tries to reconnect (`questAdbHost`, then mDNS + `adb connect`), so the real gap is a bit longer. The page usually opens 5-10 s after the headset wakes. Clicking again while one is queued just shows it. The wait ends when the page opens, after 7 minutes (*Quest did not wake ... - nothing opened*), or when the companion quits.

## Open on Quest: normal tab, signed in

The open itself is quest_tools' `Open-QuestPage` (one tab reused, VIEW intent, sign-in and plain reload, empty new-tab pages closed, `isSecureContext` and the flag fix): [quest_tools](../../../../quest_tools/README.md#opening-a-page-push-to-quest) README, *Opening a page*. What Loop Segments adds:

1. **The control page first**, in its own tab, signed in the same way (below), so the LAN page ends up in front.
2. **One LAN tab:** a tab already open on any phone LAN origin (LAN page or `/xr`) is reused, extra LAN tabs are closed. Reusing an `/xr` tab replaces the XR player with the LAN page.
3. **Signed in** with `http://admin:<password>@<phone>:8765/`, then reloaded plain: the page is signed in, its URL has no password, `fetch()` works (`status_lists.json`), and **WebXR immersive VR/AR is available**. If the tab ends on Chromium's error page (phone app closed or phone off Wi-Fi), the button reports a failure instead of "Opened".
4. Keep Alive: +60 min on the phone after the page opened (`Keep Alive: +60 min after Open on Quest`).

Always a **normal** tab: **Quest Browser disables immersive WebXR in private tabs**, so the XR player could not enter VR from one. That is also why a private tab cannot keep the LAN page out of history: the page has to run in a normal tab, so the quit deletes its history instead (why, in full: [quest_tools](../../../../quest_tools/README.md#opening-a-page-push-to-quest) README, *Always a normal tab, so history has to be cleaned*). The `questIncognito` private-tab option is gone; a leftover `"questIncognito"` in `loop-segments-windows.json` is ignored.

The password comes from `webdavPassword` in `windows\loop-segments-windows.json`, or from the matching `phoneLanHosts[].webdavPassword`. It is percent-encoded, read by the script itself (never on a command line), and never logged. Chromium does not keep the `user:pass@` form in browsing history. `"questSendLanLogin": false` (or `-NoLanLogin`) opens the plain URL and you sign in as `admin` / the app password on the headset.

## chrome://flags: insecure origin as secure

Quest WebXR over LAN `http://` needs `chrome://flags/#unsafely-treat-insecure-origin-as-secure` **Enabled** with the phone's origin listed. After Open on Quest opens the LAN tab, `isSecureContext` is read in it; only when it is **false** is the flag fixed (Quest Browser restarts, the LAN page is opened again): how, and why it is checked this way: [quest_tools](../../../../quest_tools/README.md#opening-a-page-push-to-quest) README, *Opening a page*, step 5. For Loop Segments the flag gets **every phone LAN origin** (`phoneLanHost` / `phoneLanHosts` with `lanPort`, plus the companion's current phone address), added to what it already lists, and the helper tab is the phone's no-login `/xr-assets/lsclean` (or its PC fallback). The companion no longer checks the flag at startup (there is no LAN tab to read then); the first Open on Quest does it. Manual run through `chrome://flags`: `-EnsureFlags`, which has no LAN tab, so it reopens `chrome://flags` after the restart to confirm instead.

**Reset all flags:** run [`Reset-QuestBrowserFlags.ps1`](Reset-QuestBrowserFlags.ps1) (`windows\quest\`; or `Watch-LoopSegmentsQuestLanTab.ps1 -Url ... -ResetFlags`). It does `chrome://flags` *Reset all* on the headset (the page's own `resetAllFlags`), restarts Quest Browser (which closes its open tabs) and checks that the insecure-origin flag is back to *Default* (not enabled) afterwards; its origin list text survives *Reset all*, which does nothing while the flag is off. Then it cleans up after itself like the quit: deletes its helper page from history, sweeps its *Experiments* / new-tab / blank items out of *Recently closed*, and closes Quest Browser again if it was not running before the reset. Tested: about 20 s once the headset was on adb, flag `enabled=True` → `enabled=False`; from a closed browser: 4 *Recently closed* items swept and the browser closed again. That flag is reset too, so WebXR on the LAN page is off until the next Open on Quest, which finds `isSecureContext` false and sets it again (one more browser restart). Needs the phone LAN page up (its helper tab starts on a phone page) and the headset worn. Like `Set-LoopSegmentsQuestProximitySensor.ps1` (below; shared code in [`QuestWrapperCommon.ps1`](QuestWrapperCommon.ps1) and quest_tools' `QuestWrapperCommon.ps1`), it first moves this PC to the phone's network if needed (`-SkipNetworkCheck` skips it), then keeps trying every 5 s for up to 2 minutes (`-WaitSec`) while the headset is not on adb, restarting the adb server before each retry. Exit codes 0 reset, 1 headset not on adb, 2 no adb, 3 failed.

## Keep Alive while the Quest plays

In the background the phone's LAN server (port 8765, so WebDAV and the rclone **L:** mount) only runs while Keep Alive is active, and a Keep Alive session ends **60 min** after the app was last in front or the last `POST /keep_alive.json` reset. WebDAV listings and other requests do **not** extend it. Since app build **447**, video the phone itself serves does: a video GET (Quest Browser on the phone's own `/xr` page, Skybox, rclone `L:` playback) resets the session to 60 min at most every 10 min. Since build **449** the phone's `/xr` page also posts `{"action":"playing"}` to `/keep_alive.json` once a minute while its video plays, because Quest Browser buffers a looping clip after its first pass and then sends no more video GETs (build 447 alone let Keep Alive count down mid-clip). The companion cannot see that playback (nothing on the PC serves it; seen 2026-11-26, under 50 min while a clip played on `/xr`), so the phone handles it, and the companion covers pages served from the PC (below). Before this, a session started at ~21:52 ended at 22:51: the phone refused 8765, rclone's LAN watch dropped **L:**, and a 3d_playlist_local workflow running from `L:\archive` lost its own scripts (its End session button found no shutdown script).

So the keep-awake job (above, same ~20 s loop, via quest_tools' `Invoke-QuestKeepAwakeSession -OnTick`) also asks quest_tools' **`Get-QuestMediaActivity`** whether any of our pages is playing: [quest_tools](../../../../quest_tools/README.md#quest-media-activity) README, *Quest media activity* (one `%TEMP%\quest-media-activity-<owner>.json` per project). Today the writer is 3d_playlist_local's XR server (`serve_xr_page.py`, owner `playlist`), on each `/media` request (the `<video>` fetching a segment; at most every 15 s). Only our own pages make those requests, so YouTube or any other Quest Browser playback does not count (`dumpsys audio` would: it reports playback per app, with no URL).

- **Playing** = a media request from any owner **≤ 3 min** ago: `POST /keep_alive.json` `{"action":"reset","reason":"quest_playback"}` (a fresh 60 min), again every **10 min** while it plays. Log once: `Keep Alive: Quest playing (playlist, ...) - phone session reset to 60 min`.
- Both Keep Alive calls (this reset and the +60 min after Open on Quest) go through one function, `Send-PhoneKeepAlive` in `Watch-LoopSegmentsQuestLanTab.ps1`. It stays in this repo, not quest_tools: `/keep_alive.json` is the iPhone app's, with the phone's login from this repo's config.
- **Stopped** (paused, page closed, workflow ended): nothing more is sent; the phone's timer runs out on its own, at most 60 min later. Log: `Keep Alive: Quest playback stopped`.
- **Phone not answering**: `Keep Alive: Quest playing but the phone reset failed (...)`, logged once per distinct error, retried every 60 s. A phone whose server already stopped cannot be reached this way: bring Loop Segments to the front once.
- The phone address is re-read from the companion's `lan_config.json` on every check (the companion passes `-LanConfig`), so a new phone IP mid-session is picked up. The keep-awake that 3d_playlist_local starts for itself (`-RestoreProximity`) does not send resets.
- Tested 2026-11-26 on the phone: the session end moved from 06:31:15 to 06:32:18 UTC (60 min after the reset).

## Keep the headset awake during the session

Deleting the Loop Segments history at quit needs the headset on adb with Quest Browser answering. An asleep Quest stays on Wi-Fi and adb only for a while (how long is up to the Quest's power management) and then drops off; even before that, Quest Browser does not answer while it sleeps. So while the companion runs, a hidden job holds the **proximity sensor off** (`am broadcast -a com.oculus.vrpowermanager.prox_close`: the headset acts as if worn and does not sleep when you take it off). It checks about every 20 s and applies the override as soon as the headset is on adb **and awake**, and again after a headset reboot (a reboot clears it).

**A sleeping headset is left alone.** For a while after it goes to standby the headset stays on Wi-Fi and wireless adb, and `prox_close` there means "just put on": it wakes it (`transition from STANDBY to HEADSET_MOUNTED` in `dumpsys vrpowermanager`). So a companion started soon after a quit used to light up a headset lying on the desk. Now the job reads `mWakefulness` first and, unless it is `Awake`, only logs `Keep-awake: headset asleep (Asleep) - not waking it`; the override goes on within ~20 s of you putting the headset on (which wakes it).

**Awake is not the same as in use.** With the override on, a headset lying still stays awake but goes **idle** after about a minute, and while it is idle Quest Browser's own UI **often** does not answer (no history list, no clear dialog, sometimes no new tabs): [quest_tools](../../../../quest_tools/README.md#when-quest-browser-does-not-answer) README, *When Quest Browser does not answer*. Pages in tabs that are already open still answer, so Open on Quest works on an idle headset when the LAN and control tabs are already open (`reused open tab`: seen opening signed in, `isSecureContext` read, 4 min into idle), while a click that needs new tabs may stall. SKYBOX edits and the sensor also still work. (A `Page.navigate timeout` in the log usually means the phone's LAN page is down.) That is why the history delete at quit often fails when nobody is wearing the headset; see [After-quit history helper](#after-quit-history-helper).

**Reading the headset state** (`mWakefulness`, `Virtual proximity state`, `State` / `Device idle state`): [quest_tools](../../../../quest_tools/README.md) README, *Headset state*. Open on Quest and keep-awake read `mWakefulness`; keep-awake and `-EnableProximity` the override; the after-quit helper worn = `HEADSET_MOUNTED` **and** `Not idle`. With the override `CLOSE`, `State` is always `HEADSET_MOUNTED`, even on the desk, so during a session only `Not idle` tells worn from lying still.

**Why it keeps checking:** one `prox_close` at startup would not last the session. The headset is often asleep or off adb when the companion starts, a reboot (also an OS update) clears the override, and anything else can turn the sensor back on (`Set-LoopSegmentsQuestProximitySensor.ps1 -State On`); adb has no event for "headset connected" or "sensor changed", so the job asks. A check is cheap: with the headset on adb it is `adb devices -l` plus one `dumpsys vrpowermanager`, and nothing is sent while the state is already `CLOSE`; with the headset away it also tries mDNS and `adb connect`, with short timeouts. The 20 s is how long the sensor can stay live after the headset shows up or reboots: taken off in that window, it can fall asleep before the job catches it. The flip side: a manual **On** while the companion runs is undone within ~20 s.

Cleanup, on a normal quit and on console X (the watchdog), stops that job and starts **one background process** that closes the LAN tabs, **deletes the Loop Segments history entries** (the headset is still awake), then **turns the sensor back on**. The companion closes Chromium and syncs the profile meanwhile, and waits for that process (at most 40 s from its start) before the Wi-Fi probe / router restart, which would drop the Quest's adb. Each step logs its duration (`Tabs: ... (0.4 s)`, `History step: ...`, `Proximity step: ...`, `Cleanup: finished ... s after start`). The sensor is turned back on even if the history clear failed (`am broadcast -a com.oculus.vrpowermanager.automation_disable`, checked against `dumpsys vrpowermanager`: `Virtual proximity state: DISABLED`).

Things this does not cover: pressing the power button or a flat battery still sleeps the headset. If the PC crashes or both companion processes are killed, nothing turns the sensor back on: run `-EnableProximity` (or `Set-LoopSegmentsQuestProximitySensor.ps1`, below), or reboot the headset. While the override is on, the display stays lit when the headset is off your head (battery, and keep the lenses out of direct sunlight). `"questKeepAwakeDuringSession": false` turns both halves off.

**Toggle by hand:** run [`Set-LoopSegmentsQuestProximitySensor.ps1`](Set-LoopSegmentsQuestProximitySensor.ps1) (`windows\quest\`). It first makes sure this PC is on the phone's network, as the companion's startup does (`lan\Invoke-LoopSegmentsGatewayWifiRebootIfNeeded.ps1 -PhoneLanHost <phoneLanHost>`; `-SkipNetworkCheck` skips it), since adb reaches the headset only from the same network, then runs quest_tools' `Set-QuestProximitySensor.ps1` with `-NoNetworkCycle` (its saved-Wi-Fi cycle, `Find-QuestWifiNetwork.ps1`, could move the PC off the phone's network) (retries for up to 2 min, `-State On` / `Off`, `-NoWait`; the *Proximity sensor OFF* notification): [quest_tools](../../../../quest_tools/README.md) README, *Proximity sensor*. While the companion runs, its keep-awake job switches the sensor off again within ~20 s of turning it on.

## Close LAN tabs on companion close

Before the history clear, every Quest Browser tab whose address is a phone LAN origin (the LAN page, `/xr`, ...), the Quest control page on this PC, a `questPlaylistHistoryOrigins` entry, or a page any project registered in quest_tools' shared origin list (`%TEMP%\quest-browser-origins.json`: [quest_tools](../../../../quest_tools/README.md) README, *Quest Browser cleanup*) is closed over DevTools; other tabs stay. The tab closing, history delete and sweep run in quest_tools' `Invoke-QuestBrowserCleanup`; this script supplies its own origins, the helper page and the after-quit helper. How the tabs are closed (one tab always kept as a new-tab page, because the History list needs one): [quest_tools](../../../../quest_tools/README.md#closing-tabs-and-the-browser) README, *Closing tabs and the browser*. Control page tabs and history entries are matched on every control page address opened on the headset (`%TEMP%\loopsegments-quest-control-origins.json`, last 8), not only the current one: the current address is worked out from this PC's route to the headset, which changes when the headset moves to another network. `"questCloseLanTabsOnExit": false` keeps them open.

**Quest Browser closed again when only empty tabs are left.** After the tabs, history and *Recently closed* sweep, the quit force-stops Quest Browser whenever no tab of yours is left, whoever started it ([quest_tools](../../../../quest_tools/README.md#closing-tabs-and-the-browser) README): step summary `browser closed`, or `browser left` when a tab of your own keeps it running. When the history delete is postponed, the [after-quit history helper](#after-quit-history-helper) closes it after its delete instead (`browser helper`). Needs `questCloseLanTabsOnExit`. Open on Quest still notes whether Quest Browser was running with tabs of yours (`%TEMP%\loopsegments-quest-browser-ours.json`, reset at each companion start, logged `Browser: Quest Browser was not running before Open on Quest ...`), but that no longer decides the close: it used to, and a browser this session never opened (headset off adb at Open on Quest or at a 3d_playlist_local workflow start) stayed up on a blank tab.

## Delete Loop Segments history on companion close

Deletes **only this app's entries** from Quest Browser history: every entry whose origin is a phone LAN origin (`-Url`, `phoneLanHost`, `phoneLanHosts` with `lanPort`: the LAN page, `/xr`, its assets), the Quest control page on this PC (`http://<PC address>:18766`), a `questPlaylistHistoryOrigins` entry, or a page in quest_tools' shared origin list (e.g. 3d_playlist_local's XR page). **The rest of your history is kept**, and so are cookies, cache, saved passwords, form data and site settings. How the delete, its re-check and its fallback work: [quest_tools](../../../../quest_tools/README.md#history-delete) README, *History delete*. Logged as `History: deleted 2 entries on http://10.0.100.10:8765, http://10.0.100.244:18766; kept the other 2.`

Only the current origins are matched. The PC address is worked out again at quit (see [Quest control page](#quest-control-page)). Entries from a phone address no longer in the config, or from an earlier PC address (for example after DHCP gave the PC a new IP), stay. Only the fallback catches those, and only from its range, if it runs.

**Fallback.** If the selective delete fails (at quit, or in the [after-quit history helper](#after-quit-history-helper)), all Quest Browser history from the **last 24 hours** is cleared instead (history only): `"questClearHistoryFallback"` picks the range, `hour`, `day` (default), `week`, `fourweeks`, `all`, or `none` for no fallback (the step is then just `failed`). It deletes unrelated browsing in that range; see quest_tools for how and why it is only the fallback.

The whole step is limited to **30 s** at quit (about 28 s from the cleanup's start); with the browser already running it takes 1-3 s, and a cold start may not fit (logged). Manual run: `-ClearHistory`. Set `"questClearHistoryOnExit": false` to keep these entries.

**Recently closed.** Every tab closed over DevTools lands in *Recently closed* (also shown as tiles on the new-tab page), and deleting a page from history does not reliably drop its item. So after the history delete, the quit (and the [after-quit history helper](#after-quit-history-helper)) **sweeps Recently closed**: our items are reopened, sent to a helper page and closed, and the next delete removes them. How and why: [quest_tools](../../../../quest_tools/README.md#recently-closed) README, *Recently closed*. Logged `Recently closed: cleaned N of M ... item(s)` and `Recently closed: helper visit is / NOT in the History list`. Loop Segments' helper page is the phone's `http://<phone>:8765/xr-assets/lsclean` (a small 404 page, no login; visits to the old helper `/xr-assets/aframe.min.js`, a 1.4 MB script, stopped being recorded). It must be reachable from the headset. When the phone does not answer (Loop Segments app closed, phone off the LAN; seen at an End session without the companion, which left two `.../xr-assets/lsclean` items), quest_tools serves the same small 404 page from this PC at `http://<pc>:<questControlPort + 1>/lsclean` (default 18767) and that origin is deleted with the others (logged `Helper page: 10.0.100.10:8765 not answering - serving it from this PC at ...`; [quest_tools](../../../../quest_tools/README.md#recently-closed) README). On another Wi-Fi network the items stay until the next cleanup on the phone LAN. Read-only checks: `Watch-LoopSegmentsQuestLanTab.ps1 -Url <phone LAN url> -ListHistory` (every history entry's origin + path), `-ProbeRecentlyClosed` (open tabs, Recently closed items, freshly requested); `-TestHelperVisit` checks that a helper visit is recorded (makes and deletes one). The flag fix closes its helper tab the same way.

This relies on Quest Browser's internal UI, which an update can change; the selective delete then fails (for example `History list not found`) and the fallback runs ([quest_tools](../../../../quest_tools/README.md#history-delete) README).

### Wi-Fi off at close

By default (`"questWifiOffOnExit": true`; `false` turns it off), the companion close switches the headset's **Wi-Fi off** as its very last Quest step (`cmd wifi set-wifi-enabled disabled` over adb; after the tabs, history, browser, SKYBOX and the sensor, and before the companion's Wi-Fi→www AP bounce). A sleeping headset on Wi-Fi drains its battery faster, and with Wi-Fi off it also cannot hop to the other network when the bounce reboots the phone network's router. Just before, it opens **Settings > Wi-Fi** (`am start -a android.settings.WIFI_SETTINGS`, which Quest relays to its Settings app on the Wi-Fi page with the toggle; log `Wi-Fi settings: opened`), so switching Wi-Fi back on is one tap when you next put the headset on. Only on an awake headset, since an activity start may wake a sleeping one, and after all browser steps, since Quest Browser goes behind the panel. adb drops right after (it runs over that Wi-Fi): log `Wi-Fi: switched the headset's Wi-Fi off`, step summary `Wi-Fi off`. Not done while the history delete is postponed (`Wi-Fi: left on - ...`): the [after-quit history helper](#after-quit-history-helper) needs it, and switches Wi-Fi off itself right after its delete, before running the held AP bounce. That happens while you are wearing the headset (the helper only deletes once it is worn), so Wi-Fi goes off under you: switch it back on if you keep using the headset. When the helper gives up at 2 h, it still switches Wi-Fi off first if the headset is on adb. Wi-Fi is not switched off before the bounce only when the headset cannot be reached then, the Wi-Fi command fails, or the quit's Quest cleanup is cut off by its time limit before its last step.

**By hand:** [`Set-LoopSegmentsQuestWifiOff.ps1`](Set-LoopSegmentsQuestWifiOff.ps1) (`windows\quest\`; or `Watch-LoopSegmentsQuestLanTab.ps1 -WifiOff`) does the same any time, whatever `questWifiOffOnExit` says. Like `Set-LoopSegmentsQuestProximitySensor.ps1` it first moves this PC to the phone's network if needed (`-SkipNetworkCheck`), then runs quest_tools' `Set-QuestWifiOff.ps1`: [quest_tools](../../../../quest_tools/README.md) README, *Wi-Fi off*.

Before the next session, switch Wi-Fi on in the headset's quick settings. Wireless debugging then comes back by itself on a new port, which the PC finds over mDNS (tested: listed 2 s after Wi-Fi came back on). Until then Open on Quest queues and keep-awake waits.

### After-quit history helper

When the history step at quit still fails (usually `history query never answered` and `dialog time options never arrived`: nobody is wearing the headset, so Quest Browser is idle, see above), or the quit cannot reach the headset at all, the delete is **postponed** instead of dropped: it goes to quest_tools' after-quit helper, which deletes the entries once you next put the headset on. You only need the headset on until Quest Browser pops up: the helper holds the sensor off for the delete, so taking it off then does not stop it (log: `headset worn - deleting (sensor held off for it: the headset can come off now)`). How it works (the pending file, the 2 s worn check, the sensor hold, the fallback once per run, Wi-Fi off after its delete, tested timings): [quest_tools](../../../../quest_tools/README.md#after-quit-history-helper) README, *After-quit history helper*. The quit's step result is then `postponed` (exit code 4; the companion prints *cleanup done ..., except the history delete*). What Loop Segments sets (`Start-LoopSegmentsHistoryRetry` in the watcher):

- it gives up after **2 hours** (`questHistoryRetryMinutes`, `0` = no helper): `History retry: the headset was not worn in time - gave up`;
- the range fallback is `questClearHistoryFallback` (default last 24 hours; `none` turns it off for the quit and the helper); Wi-Fi goes off after its delete per `questWifiOffOnExit`; the helper page is the phone's, with the PC fallback above;
- it stops when the **companion starts again** (`Run-PCloudWebCompanion.ps1` / `_run_chromium.ps1`): the new session's quit deletes the same origins, old entries included. The companion also stops it first thing at startup (`QuestCompanionHooks.ps1` `Stop-QuestHistoryRetry`, before keep-awake can switch the sensor off under it), and so does a 3d_playlist_local workflow start;
- **it holds the quit's Wi-Fi AP bounce.** When the quit's Wi-Fi→www check fails while this helper is waiting, the companion does not restart the phone network's router then: that restart moves the headset to the other Wi-Fi (see [Headset on another Wi-Fi network](#headset-on-another-wi-fi-network)), where the helper on this PC cannot reach it. The check itself still runs at quit, while Loop Segments is in front (before Home); only its result is kept, in `%TEMP%\loopsegments-wifi-bounce-pending.json` (console: `[wifi-www] Quest history delete still pending: AP bounce held until ...`). The helper's after-script, [`Invoke-LoopSegmentsHeldWifiBounce.ps1`](Invoke-LoopSegmentsHeldWifiBounce.ps1), runs the bounce right after the delete (and its Wi-Fi off), or when it gives up at 2 h (`Wi-Fi bounce: history deleted - bouncing the phone LAN AP now`; the bounce's own output goes to `%TEMP%\loopsegments-wifi-bounce.log`). If the companion starts again first, the held bounce is dropped: that session's quit checks again. SideStore's daily refresh can wait those hours. None of this holds up the quit: the companion waits only for the Quest cleanup step (at most 40 s), never for the helper, and with the bounce held it goes straight on to Home and finishes; the helper runs on by itself in the background.

## Quest control page

One small page on **this PC's LAN address**, made for Quest Browser, shared by the projects that use the headset. The page itself (HTTP server, sign-in, layout, the built-in **LAN bandwidth: PC → Quest** test) is quest_tools': [`QuestControlHost.ps1`](../../../../quest_tools/QuestControlHost.ps1), see [quest_tools README, *Quest control page*](../../../../quest_tools/README.md#quest-control-page). This repo adds its tiles, [`LoopSegmentsControlTiles.ps1`](LoopSegmentsControlTiles.ps1): **SKYBOX: phone as a WebDAV server**, **LAN bandwidth: PC ↔ phone**, **Session** (an **End session: stop all** button for a session with only the companion: it runs 3d_playlist_local's `Invoke-PlaylistLocalQuestShutdown.ps1` when that repo is on this PC, else closes the companion's Chromium gracefully so its normal quit cleans up the Quest; hidden while a workflow's Session Control tile is on the page) and the recent SKYBOX log. The companion registers them at startup (`QuestCompanionHooks.ps1` → quest_tools `Register-QuestControlTiles.ps1 -Owner loopsegments`) and takes them off at close; the host starts with the first project that registers and stops by itself once none is left. 3d_playlist_local workflows add their **Session Control** tile (Space, End session, segment bitrate): see `3d_playlist_local\individual_transcode\quest\README.md`.

Default port **18766** (quest_tools `controlPort`, falling back to `questControlPort`), for example `http://10.0.100.244:18766/`. The address is not a setting: each time it is needed (Open on Quest, closing tabs and deleting history at quit) it is the PC's IPv4 address on the route to the headset (the headset's IP from its wireless adb serial, or `questAdbHost`; for a USB serial, the phone address from `-Url`). **Open on Quest** opens it in its own normal tab, signed in with the page's token link (`/s?t=<token>`, swapped for a cookie, then reloaded plain), then opens the LAN page so that one is in front; an already open control tab is reused. `"questControlPageOnQuest": false` leaves it out.

**On the PC:** **Open on Quest** also opens the page at `http://127.0.0.1:18766/` next to the LAN tab, and the companion extension answers the login, as it does for the phone LAN page: this repo's tiles give the host the phone LAN login (`webdavUser` and that phone's `phoneLanHosts[].webdavPassword`, else `webdavPassword`) as an accepted HTTP Basic login. The companion writes the port and the login into the extension's `lan_config.json` at startup (`questControlPort`, `questControlPassword`).

**Windows Firewall** must allow inbound TCP on the port on the Private network: on this PC the existing *PowerShell 7* allow rule for `pwsh.exe` already does. If a tab opens but shows Chromium's error page (`Control page: ... did not load on the Quest` in the log), allow the port yourself, or set `"questControlPage": false`. If no tab appears at all (`... VIEW intent dropped`), that is the headset UI eating the intent, not the firewall. Host log: `%TEMP%\quest-control-host.log`; action log: `%TEMP%\loopsegments-quest-lantab.log`.

## LAN bandwidth (PC ↔ phone), from the control page

The **LAN bandwidth: PC ↔ phone** section shows the last measurement and a **Measure LAN** button. The button runs the same probe the companion runs at startup, [`..\lan\Measure-LoopSegmentsLanThroughput.ps1`](../lan/Measure-LoopSegmentsLanThroughput.ps1), in the background on the PC: it downloads up to **64 MB** of a random phone video over **HTTP**, and when the rclone mount (`mountDriveLetter`, default `L:`) is up also copies it **from the mount**, then uses the **lower** number. While it runs the page shows its last output lines; it usually takes 10-60 s. One measurement at a time (a second press gets *already running*); it runs alongside a SKYBOX action.

| Row | Meaning |
|---|---|
| **Result** | Mbps of the lower path (`http` or `mount`), green; red with **LOW** when under `minLanThroughputMbps` (default 40), or *failed: ...* with the error |
| **HTTP / mount** | Each path's Mbps (*not measured* when the mount was not up) |
| **Max segment bitrate** | The recommended max media bitrate for minute segments (80% of the result, 5-80 Mbps), the same number the probe prints and writes to the phone sidecars when the mount is up |
| **Measured** | When, in the viewer's local time; notes when Virtual Desktop's streamer was running (it uses ~50 Mbps of the LAN, so the number reads low) |

Unlike the startup probe, a press **never reboots routers** when the result is low (`-SkipLowThroughputGatewayReboot`): only the companion's startup probe does that. The result is kept on the PC in `%TEMP%\loopsegments-lan-throughput.json` (`-ResultFile`; the startup probe writes it too, so the page shows that one until you press the button); the output of the last press is in `%TEMP%\loopsegments-quest-control-lanbw.log`. The phone LAN page's own **LAN speed test** measures the browser ↔ phone path instead (on the Quest: headset ↔ phone).

## SKYBOX: phone as a WebDAV server, from the control page

SKYBOX VR Player (`xyz.skybox.player.ovr`) keeps its **Network** servers in an SQLite file on the headset's shared storage, `/sdcard/Android/data/xyz.skybox.player.ovr/files/SkyboxDataBase` (table `DeviceDataTable`). A WebDAV server is one row: `Url` `webdav://<phone>:8765/`, `FileName` (the name shown), `Username`, and `Password` **in plain text** (SKYBOX stores it that way itself).

The control page has three buttons; each runs once in the background (quest_tools' `QuestSkybox.ps1` through `Watch-LoopSegmentsQuestLanTab.ps1`), one at a time:

| Button | What it does |
|---|---|
| **Push** | Put server **Loop Segments** in SKYBOX at the phone's **current** address with the **current** login, and delete the servers this PC added at older addresses |
| **Update** | The same, but only if such a server is already there (else *not there*, nothing touched) |
| **Clear** | Remove every Loop Segments entry from SKYBOX's Network list (below; asks first) |

Current means read when you press the button: the phone address and port from the companion's `lan_config.json` (`phoneLanHost`, `lanPort`; written from `phoneLanHostSource`: the saved `phoneLanHost`, or the USB-detected address), and the login from `windows\loop-segments-windows.json` (`webdavUser`, `phoneLanHosts[].webdavPassword` for that phone, else `webdavPassword`). Nothing runs on a timer: after the phone's address or the password changes, press **Update** (or **Push**). Opening the server in SKYBOX → Network needs no login. A press while the headset is off adb reports *headset not on adb* and changes nothing.

Every server URL this PC added is listed (URLs only, no password) in `%TEMP%\loopsegments-skybox-webdav.json`. **At companion close** (and on **Clear**) the cleanup removes, in one edit after the history clear, every **Loop Segments entry** in SKYBOX's Network list, so no phone password stays on the headset after a session:

- WebDAV servers this PC added (the list above);
- any WebDAV server at a phone address the companion knows: the current one in `lan_config.json`, `phoneLanHost`, and every `phoneLanHosts[]` entry with `lanPort`, including servers you added by hand under another name;
- any WebDAV server named **Loop Segments**, wherever it points;
- the companion's **rclone DLNA** server: a `dlna://` entry named `rcloneDlnaName` (default *Loop Segments*) that rclone announced (`Manufacturer` *rclone (rclone.org)*). SKYBOX finds it again by itself the next time `-EnableRcloneDlna` serves it.

Everything else stays: other WebDAV, SMB and AirScreen servers, other DLNA servers (also one named *Loop Segments* that rclone did not announce), SKYBOX's folder cache and playback positions. The log lists what was removed (`SKYBOX: removed 2 Loop Segments entries: webdav://10.0.100.10:8765/, rclone DLNA 'Loop Segments'`), and the list file is deleted afterwards.

At close the cleanup first stops the control page and any button action still running (whole process trees, adb included), so nothing adds the server back. An action stopped in the middle of an edit leaves its `%TEMP%\loopsegments-skybox-*` folder (a full copy of SKYBOX's database, saved logins included) and maybe a half-pushed `SkyboxDataBase.loopsegments-new` on the headset; every SKYBOX run, the close-time removal included, deletes those first and logs it (`removed leftovers of an interrupted run`). The swap itself is a single `mv`, so SKYBOX's file is always either the old or the new copy.

How a change is made (copy, check with `sqlite3`, stop SKYBOX only when the row changes, guarded swap), what happens to an open SKYBOX, and what to do if a SKYBOX update changes its database: [quest_tools](../../../../quest_tools/README.md) README, *SKYBOX database*. Each copy moves the whole file (about 60 MB, 5-10 s over Wi-Fi), so with this on the companion waits up to **60 s** for the close-time cleanup instead of 40 s.

So SKYBOX is only touched when the server has to change: if it is open, **Push** / **Update** **restart** it (closed, edited, opened again on its home screen; anything playing stops; if nobody is wearing the headset the reopen may not happen, see below) and **Clear** or the close-time removal **closes** it. If it is closed, it stays closed. While the server is in SKYBOX, its password is on the headset in plain text, readable over adb. If the companion is killed outright, the server stays: press **Clear** next session, run `-ClearSkyboxWebDav` (below), or delete it in SKYBOX. `"questSkyboxWebDav": false` turns off the buttons and the close-time removal.

### Headset on another Wi-Fi network

mDNS does not cross routers, so the PC finds the headset only while both are on the same network (subnet). Off it, the headset still answers ping at its new address, but `adb mdns services` stops listing it, `adb devices` shows the old serial as *offline*, and each switch gives wireless debugging a new port. Restarting the adb server does not help.

The usual cause is the companion's own **quit**, and it is intended: when its Wi-Fi→www check fails, the finish restarts the Wi-Fi of the phone network's router (held until the [after-quit history helper](#after-quit-history-helper) is done, when one is waiting: the helper needs the headset on the PC's network) (`[gateway] Rebooting phone-LAN AP 10.0.100.2 (mr5100)` in the console log; see [../README.md](../README.md)). That restart is what gives the phone internet over Wi-Fi again, which SideStore needs for its daily app refresh, so it stays. While that router is down, Windows and the headset both join their other saved network (seen: from `ATT-WIFI-5pmY_5GHz`, `10.0.100.x`, the phone's network, to `ATT-WIFI-3pKe`, `192.168.2.x`), seconds after every quit, and stay there. The next companion start moves the PC back to the phone's network; the headset may stay behind, and adb loses it until it moves back too (or you move it). Windows' Wi-Fi log shows this: Event Viewer → *Applications and Services Logs → Microsoft → Windows → WLAN-AutoConfig → Operational*, event 8001.

So do **not** simply forget the other network on the headset: after a quit the PC sits on it, and the [after-quit history helper](#after-quit-history-helper) then only finds a headset that followed it there (tested: both on `192.168.2.x`, found over mDNS 22 s after the quit). While the companion runs, both need the phone's network; if the headset is the one that stayed behind, switch it in its Wi-Fi settings, and the companion finds it within about 20 s.

## Settings (`windows\loop-segments-windows.json`)

| Key | Default | Meaning |
|-----|---------|---------|
| `questAdbHost` | `""` | Headset Wi‑Fi IP for `adb connect` (empty = already-connected / mDNS only) |
| `questAdbPort` | `5555` | Port for `questAdbHost` |
| `questAdbSerial` | `""` | Pick this adb serial when several Android devices are connected |
| `questAdbExe` | `""` | Full path to `adb.exe` (empty = auto) |
| `questAdbRediscoverSec` | `60` | Headset not found for this long and no adb device connected: restart the PC's adb server once to rediscover it over mDNS (at most every 5 min). `0` = off |
| `questSendLanLogin` | `true` | Sign the tab in with the LAN login (`false` = sign in on the headset) |
| `questEnsureInsecureOriginFlag` | `true` | Each Open on Quest: check `isSecureContext` in the LAN tab and, only if false, fix the insecure-origin flag (restarts Quest Browser and reopens the page) |
| `questClearHistoryOnExit` | `true` | Companion close: delete the Quest Browser history entries on the phone LAN page, the control page and every page in quest_tools' shared origin list (other history is kept) |
| `questWifiOffOnExit` | `true` | Companion close: open Settings > Wi-Fi, then switch the headset's Wi-Fi off as the last step (see [Wi-Fi off at close](#wi-fi-off-at-close)) |
| `questHistoryRetryMinutes` | `120` | The quit could not delete the history (headset not worn / not on adb): a background helper deletes it once the headset is worn, for up to this many minutes. `0` = off |
| `questClearHistoryFallback` | `"day"` | If that selective delete fails (at quit or in the after-quit helper): clear **all** history from this range instead (`hour`, `day`, `week`, `fourweeks`, `all`; `none` = no fallback) |
| `questCloseLanTabsOnExit` | `true` | Companion close: close Quest Browser tabs on the phone LAN page (before the history clear), then Quest Browser itself if Open on Quest started it and no other tabs are left |
| `questControlPage` | `true` | Companion session: this repo's tiles on the Quest control page (quest_tools hosts it) |
| `questControlPort` | `18766` | Its TCP port, read by quest_tools when its own `controlPort` is not set (Windows Firewall must allow it inbound on the Private network) |
| `questControlPageOnQuest` | `true` | **Open on Quest** also opens the control page in its own tab on the headset (the PC Chromium tab opens whenever `questControlPage` is on) |
| `questSkyboxWebDav` | `true` | Control page SKYBOX **Push / Update / Clear** buttons, and removal of the Loop Segments entries (phone WebDAV servers, rclone DLNA entry) at companion close |
| `questKeepAwakeDuringSession` | `true` | Hold the proximity sensor off while the companion runs (headset stays awake for the close-time history clear); turned back on at cleanup |
